# Одинарні та розділені запити

## Проблеми з продуктивністю окремих запитів

Під час роботи з реляційними базами даних EF завантажує пов'язані об'єкти, вводячи JOIN в один запит. Хоча JOIN-операції є досить стандартними під час використання SQL, вони можуть створювати значні проблеми з продуктивністю, якщо їх використовувати неправильно. На цій сторінці описано ці проблеми з продуктивністю та показано альтернативний спосіб завантаження пов’язаних об’єктів, який їх обходить.

## Декартів вибух.

Розглянемо наступний запит LINQ та його перекладений SQL-еквівалент:

```cs
    var query = context.Blogs
            .Include(b => b.Posts)
            .Include(b => b.Contributors);

    var blogs = await query.ToListAsync();

    Console.WriteLine(query.ToQueryString());
```
```sql
SELECT [b].[BlogId], [b].[Url], [p].[PostId], [p].[BlogId], [p].[Content], [p].[Title], [c].[ContributorId], [c].[BlogId], [c].[Name]
FROM [Blogs] AS [b]
LEFT JOIN [Posts] AS [p] ON [b].[BlogId] = [p].[BlogId]
LEFT JOIN [Contributors] AS [c] ON [b].[BlogId] = [c].[BlogId]
ORDER BY [b].[BlogId], [p].[PostId]
```

У цьому прикладі, оскільки і Posts, і Contributors є навігаціями колекцій у Blog — вони знаходяться на одному рівні — реляційні бази даних повертають векторний добуток: кожен рядок з Posts об’єднується з кожним рядком з Contributors. Це означає, що якщо певний блог має 10 публікацій і 10 авторів, база даних повертає 100 рядків для цього єдиного блогу.
Це явище, яке іноді називають декартовим вибухом, може призвести до ненавмисної передачі величезних обсягів даних клієнту, особливо коли до запиту додається більше братніх JOIN; це може бути серйозною проблемою продуктивності в програмах баз даних. 

Зверніть увагу, що декартівський розпад не відбувається, коли два об'єднання JOIN не знаходяться на одному рівні:

```cs
    var query = context.Blogs
        .Include(b => b.Posts)
        .ThenInclude(p => p.Comments);

    var blogs = await query.ToListAsync();

    Console.WriteLine(query.ToQueryString());
```

```sql
SELECT [b].[BlogId], [b].[Url], [s].[PostId], [s].[BlogId], [s].[Content], [s].[Title], [s].[CommentId], [s].[CommentText], [s].[PostId0]
FROM [Blogs] AS [b]
LEFT JOIN (
    SELECT [p].[PostId], [p].[BlogId], [p].[Content], [p].[Title], [c].[CommentId], [c].[CommentText], [c].[PostId] AS [PostId0]
    FROM [Posts] AS [p]
    LEFT JOIN [Comment] AS [c] ON [p].[PostId] = [c].[PostId]
) AS [s] ON [b].[BlogId] = [s].[BlogId]
ORDER BY [b].[BlogId], [s].[PostId]
```

У цьому запиті Comments – це навігаційна колекція Post, на відміну від Contributors у попередньому запиті, який був навігаційною колекцією Blog. У цьому випадку для кожного коментаря, який має блог (через його публікації), повертається один рядок, і векторний добуток не виникає.

## Дублювання даних

Об'єднання JOIN може створювати ще один тип проблем із продуктивністю. Розглянемо наступний запит, який завантажує лише одну навігацію колекції:

```cs
    var query = context.Blogs
            .Include(b => b.Posts);
  
    var blogs = await query.ToListAsync();

    Console.WriteLine(query.ToQueryString());
```
```sql
SELECT [b].[BlogId], [b].[HugeColumn], [b].[Url], [p].[PostId], [p].[BlogId], [p].[Content], [p].[Title]
FROM [Blogs] AS [b]
LEFT JOIN [Posts] AS [p] ON [b].[BlogId] = [p].[BlogId]
ORDER BY [b].[BlogId]
```
Переглядаючи прогнозовані стовпці, кожен рядок, повернутий цим запитом, містить властивості з таблиць Blogs та Posts; це означає, що властивості блогу дублюються для кожної публікації в блозі. Хоча зазвичай це нормально і не викликає проблем, якщо таблиця Blogs містить дуже великий стовпець (наприклад, двійкові дані або величезний текст), цей стовпець буде дублюватися та надсилатися назад клієнту кілька разів. Це може значно збільшити мережевий трафік і негативно вплинути на продуктивність вашої програми.

Якщо вам насправді не потрібен величезний стовпець, його легко просто не запитувати:

```cs
    var query = context.Blogs
            .Include(b => b.Posts);
  
    var blogs = await query.ToListAsync();

    Console.WriteLine(query.ToQueryString());
```
```sql
SELECT [b].[BlogId], [b].[Url], [p].[PostId], [p].[BlogId], [p].[Content], [p].[Title]
FROM [Blogs] AS [b]
LEFT JOIN [Posts] AS [p] ON [b].[BlogId] = [p].[BlogId]
ORDER BY [b].[BlogId]
```

Використовуючи проекцію для явного вибору потрібних стовпців, ви можете пропустити великі стовпці та покращити продуктивність; зверніть увагу, що це гарна ідея незалежно від дублювання даних, тому подумайте про те, щоб зробити це навіть тоді, коли не завантажується Колекцію навігації. Однак, оскільки це проектує блог до анонімного типу, EF не відстежує блог, і зміни до нього не можна зберегти назад як завжди.

Варто зазначити, що на відміну від декартового вибуху, дублювання даних, спричинене JOIN, зазвичай не є значним, оскільки розмір дубльованих даних незначний; зазвичай це те, про що варто турбуватися, лише якщо у вашій головній таблиці є великі стовпці.

## Розділені запити

Щоб обійти проблеми з продуктивністю, описані вище, EF дозволяє вказати, що заданий запит LINQ слід розділити на кілька запитів SQL. Замість JOIN, розділені запити генерують додатковий SQL-запит для кожної включеної навігації колекції:

```cs
    var query = context.Blogs
        .Include(blog => blog.Posts)
        .AsSplitQuery();

    var blogs = await query.ToListAsync();

    Console.WriteLine(query.ToQueryString());
```

Це створить наступний SQL-код:

```sql
SELECT [b].[BlogId], [b].[HugeColumn], [b].[Url]
FROM [Blogs] AS [b]
ORDER BY [b].[BlogId]

SELECT [p].[PostId], [p].[BlogId], [p].[Content], [p].[Title], [b].[BlogId]
FROM [Blogs] AS [b]
INNER JOIN [Posts] AS [p] ON [b].[BlogId] = [p].[BlogId]
ORDER BY [b].[BlogId]
```
Попередження

Під час використання розділених запитів із Skip/Take у версіях EF до 10 зверніть особливу увагу на те, щоб упорядкування запитів було повністю унікальним; невиконання цієї вимоги може призвести до повернення неправильних даних. Наприклад, якщо результати впорядковані лише за датою, але може бути кілька результатів з однаковою датою, то кожен із розділених запитів може отримати різні результати з бази даних. Упорядкування за датою та ідентифікатором (або будь-якою іншою унікальною властивістю чи комбінацією властивостей) робить упорядкування повністю унікальним та уникає цієї проблеми. Зауважте, що реляційні бази даних не застосовують жодного впорядкування за замовчуванням, навіть для первинного ключа.

Примітка

One-to-one пов'язані сутності завжди завантажуються через JOIN в одному запиті, оскільки це не впливає на продуктивність.

## Глобальне ввімкнення розділених запитів

Ви також можете налаштувати розділені запити як запити за замовчуванням для контексту вашої програми:

```cs
protected override void OnConfiguring(DbContextOptionsBuilder optionsBuilder)
{
    optionsBuilder
        .UseSqlServer(
            @"Server=(localdb)\mssqllocaldb;Database=EFQuerying;Trusted_Connection=True;ConnectRetryCount=0",
            o => o.UseQuerySplittingBehavior(QuerySplittingBehavior.SplitQuery));
}
```
Навіть якщо розділені запити налаштовано за замовчуванням, все ще можна налаштувати виконання певних запитів як окремих запитів:

```cs
    var blogs = await context.Blogs
        .Include(blog => blog.Posts)
        .AsSingleQuery()
        .ToListAsync();
```
EF Core використовує режим одного запиту за замовчуванням за відсутності будь-якої конфігурації. Оскільки це може спричинити проблеми з продуктивністю, EF Core генерує попередження щоразу, коли виконуються такі умови:

* EF Core виявляє, що запит завантажує кілька колекцій.
* Користувач не налаштував режим розділення запитів глобально.
* Користувач не використав оператор AsSingleQuery/AsSplitQuery у запиті.

Щоб вимкнути попередження, налаштуйте режим розділення запитів глобально або на рівні запиту на відповідне значення.

## Характеристики розділених запитів

Хоча розділений запит дозволяє уникнути проблем із продуктивністю, пов'язаних з об'єднаннями JOIN та декартовим розкладом, він також має деякі недоліки:

* Хоча більшість баз даних гарантують узгодженість даних для окремих запитів, таких гарантій немає для кількох запитів. Якщо база даних оновлюється одночасно під час виконання запитів, результуючі дані можуть бути неузгодженими. Ви можете зменшити це, об'єднавши запити в серіалізовану транзакцію або транзакцію знімків, хоча це може створити власні проблеми з продуктивністю. Для отримання додаткової інформації див. документацію до вашої бази даних.

* Кожен запит наразі передбачає додатковий мережевий цикл передачі даних до вашої бази даних. Кілька мережевих циклів передачі даних можуть знизити продуктивність, особливо там, де затримка передачі даних висока (наприклад, хмарні сервіси).

* Хоча деякі бази даних дозволяють використовувати результати кількох запитів одночасно (SQL Server з MARS, Sqlite), більшість дозволяють активному лише одному запиту в будь-який момент. Отже, всі результати попередніх запитів повинні бути буферизовані в пам'яті вашої програми перед виконанням наступних запитів, що призводить до збільшення вимог до пам'яті.

* Під час включення навігації за посиланнями, а також навігації за колекціями, кожен із розділених запитів включатиме об’єднання з навігацією за посиланнями. Це може знизити продуктивність, особливо якщо навігацій за посиланнями багато.

На жаль, не існує єдиної стратегії завантаження пов'язаних сутностей, яка б підходила для всіх сценаріїв. Уважно розгляньте переваги та недоліки одинарних та розділених запитів, щоб вибрати той, який відповідає вашим потребам.
