# SQL-запити

Entity Framework Core дозволяє переходити до SQL-запитів під час роботи з реляційною базою даних. SQL-запити корисні, якщо потрібний запит неможливо виразити за допомогою LINQ, або якщо LINQ-запит призводить до того, що EF генерує неефективний SQL. SQL-запити можуть повертати звичайні типи сутностей або типи сутностей без ключів, які є частиною вашої моделі.

## Базові SQL-запити

Ви можете використовувати FromSql для початку LINQ-запиту на основі SQL-запиту:

```cs
    var query = context.Blogs
    .FromSql($"SELECT * FROM dbo.Blogs");

    var blogs = await query.ToListAsync();

    Console.WriteLine(query.ToQueryString());

    foreach (var blog in blogs)
    {
        Console.WriteLine($"Blog:{blog.BlogId}\t{blog.Url}\t{context.Entry(blog).State} ");
    }
```
```
SELECT * FROM dbo.Blogs

Blog:1  https://devblogs.microsoft.com/dotnet   Unchanged
Blog:2  https://mytravelblog.com/       Unchanged
Blog:3  https://mytravelblog3.com/      Unchanged
```
FromSql було представлено в EF Core 7.0. Під час використання старіших версій використовуйте FromSqlInterpolated.

SQL-запити можна використовувати для виконання збереженої процедури, яка повертає дані сутності:

```sql
CREATE PROCEDURE dbo.GetMostPopularBlogs
AS
BEGIN
    -- Налаштування для підвищення продуктивності
    SET NOCOUNT ON;

    -- Вибірка блогів із рейтингом, що перевищує заданий
    SELECT 
        [BlogId],
        [Url],
        [Rating],
        [OwnerId]
    FROM 
        [dbo].[Blogs]
    WHERE 
        [Rating] > 3
END
```

```cs
var blogs = await context.Blogs
    .FromSql($"EXECUTE dbo.GetMostPopularBlogs")
    .ToListAsync();
```
```
EXECUTE dbo.GetMostPopularBlogs

https://devblogs.microsoft.com/dotnet   5
https://mytravelblog.com/       4
```

FromSql можна використовувати лише безпосередньо на DbSet. Його не можна створити поверх довільного LINQ-запиту.

## Передача параметрів

Попередження

Зверніть пильну увагу на параметризацію під час використання SQL-запитів.

Під час введення будь-яких наданих користувачем значень у SQL-запит слід бути обережним, щоб уникнути атак SQL-ін'єкцій. SQL-ін'єкція відбувається, коли програма інтегрує надане користувачем рядкове значення в SQL-запит, і надане користувачем значення створюється для завершення рядка та виконання іншої шкідливої ​​SQL-операції. 

Методи FromSql та FromSqlInterpolated захищені від SQL-ін'єкцій та завжди інтегрують дані параметрів як окремий SQL-параметр. Однак, метод FromSqlRaw може бути вразливим до атак SQL-ін'єкцій, якщо його використовувати неправильно.

У наступному прикладі збережена процедура отримує один параметр, додаючи заповнювач параметра в рядок SQL-запиту та надаючи додатковий аргумент:

```cs
var user = "johndoe";

var blogs = await context.Blogs
    .FromSql($"EXECUTE dbo.GetMostPopularBlogsForUser {user}")
    .ToListAsync();
```
Хоча цей синтаксис може виглядати як звичайна інтерполяція рядків C#, надане значення обгортається в DbParameter, а згенероване ім'я параметра вставляється туди, де було вказано заповнювач {0}. Це робить FromSql безпечним від SQL-ін'єкцій та ефективно та правильно надсилає значення до бази даних.

Під час виконання збережених процедур може бути корисним використовувати іменовані параметри в рядку SQL-запиту, особливо коли збережена процедура має додаткові параметри:

```cs
var user = new SqlParameter("user", "johndoe");

var blogs = await context.Blogs
    .FromSql($"EXECUTE dbo.GetMostPopularBlogsForUser @filterByUser={user}")
    .ToListAsync();
```

Якщо вам потрібен більший контроль над параметром бази даних, що надсилається, ви також можете створити DbParameter та надати його як значення параметра. Це дозволяє вам встановити точний тип бази даних параметра або такі аспекти, як його розмір, точність чи довжина:

```cs
var user = new SqlParameter("user", "johndoe");

var blogs = await context.Blogs
    .FromSql($"EXECUTE dbo.GetMostPopularBlogsForUser {user}")
    .ToListAsync();
```
Примітка

Параметри, які ви передаєте, повинні точно відповідати визначенню збереженої процедури. Зверніть особливу увагу на порядок параметрів, намагаючись не пропустити або не втратити жодного з них, або ж розгляньте можливість використання нотації іменованих параметрів. Також переконайтеся, що типи параметрів відповідають, а їхні аспекти (розмір, точність, масштаб) встановлено належним чином.

## Динамічний SQL та параметри

FromSql та його параметризацію слід використовувати скрізь, де це можливо. Однак, існують певні сценарії, коли SQL потрібно динамічно об'єднувати, і параметри бази даних не можна використовувати. Наприклад, припустимо, що змінна C# містить назву властивості, за якою потрібно фільтрувати. Може виникнути спокуса використати SQL-запит, подібний до наступного:

```cs
var propertyName = "User";
var propertyValue = "johndoe";

var blogs = await context.Blogs
    .FromSql($"SELECT * FROM [Blogs] WHERE {propertyName} = {propertyValue}")
    .ToListAsync();
```
Цей код не працює, оскільки бази даних не дозволяють параметризувати імена стовпців (або будь-яку іншу частину схеми).

По-перше, важливо врахувати наслідки динамічного побудови запиту – через SQL чи іншим чином. Прийняття імені стовпця від користувача може дозволити йому вибрати стовпець, який не індексовано, що призведе до надзвичайно повільного виконання запиту та перевантаження бази даних; або це може дозволити їм вибрати стовпець, що містить дані, які ви не хочете розкривати. За винятком справді динамічних сценаріїв, зазвичай краще мати два запити для двох імен стовпців, ніж використовувати параметризацію для їх згортання в один запит. 

Якщо ви вирішили, що хочете динамічно створювати свій SQL, вам доведеться використовувати FromSqlRaw, який дозволяє інтерполювати змінні дані безпосередньо в рядок SQL, замість використання параметра бази даних:

```cs
var columnName = "Url";
var columnValue = new SqlParameter("columnValue", "http://SomeURL");

var blogs = await context.Blogs
    .FromSqlRaw($"SELECT * FROM [Blogs] WHERE {columnName} = @columnValue", columnValue)
    .ToListAsync();
```
У наведеному вище коді ім'я стовпця вставляється безпосередньо в SQL за допомогою інтерполяції рядків C#.Ви несете відповідальність за те, щоб це рядкове значення було безпечним, очищуючи його, якщо воно походить з небезпечного джерела; це означає виявлення спеціальних символів, таких як крапка з комою, коментарі та інші SQL-конструкції, та або їх належне екранування, або відхилення таких вхідних даних.

З іншого боку, значення стовпця надсилається через DbParameter, і тому є безпечним для SQL-ін'єкцій.

Попередження

Будьте дуже обережні під час використання FromSqlRaw і завжди переконайтеся, що значення або походять з безпечного джерела, або належним чином очищені. SQL-ін'єкції можуть мати катастрофічні наслідки для вашої програми.

## Композиція за допомогою LINQ

Ви можете композицію виконувати поверх початкового SQL-запиту за допомогою операторів LINQ; EF Core розглядатиме ваш SQL як підзапит і композиціюватиме його в базі даних. У наступному прикладі використовується SQL-запит, який вибирає значення з табличної функції (TVF). А потім компонує на ньому за допомогою LINQ для фільтрації та сортування.

```cs
var searchTerm = "Lorem ipsum";

var blogs = await context.Blogs
    .FromSql($"SELECT * FROM dbo.SearchBlogs({searchTerm})")
    .Where(b => b.Rating > 3)
    .OrderByDescending(b => b.Rating)
    .ToListAsync();
```
Наведений вище запит генерує наступний SQL-код:

```sql
SELECT [b].[BlogId], [b].[OwnerId], [b].[Rating], [b].[Url]
FROM (
    SELECT * FROM dbo.SearchBlogs(@p0)
) AS [b]
WHERE [b].[Rating] > 3
ORDER BY [b].[Rating] DESC
```

## Включення пов'язаних даних

Оператор Include можна використовувати для завантаження пов'язаних даних, як і з будь-яким іншим запитом LINQ:

```cs
var searchTerm = "Lorem ipsum";

var blogs = await context.Blogs
    .FromSql($"SELECT * FROM dbo.SearchBlogs({searchTerm})")
    .Include(b => b.Posts)
    .ToListAsync();
```
Композиція за допомогою LINQ вимагає, щоб ваш SQL-запит був компонованим, оскільки EF Core оброблятиме наданий SQL як підзапит. Компоновані SQL-запити зазвичай починаються з ключового слова SELECT і не можуть містити SQL-функції, які не є допустимими в підзапиті, такі як:

* Крапка з комою в кінці
* На SQL Server, підказка на рівні запиту в кінці (наприклад, OPTION (HASH JOIN))
* У SQL Server речення ORDER BY, яке не використовується з OFFSET 0 OR TOP 100 PERCENT у реченні SELECT

SQL Server не дозволяє створювати запити поверх викликів збережених процедур, тому будь-яка спроба застосувати додаткові оператори запиту до такого виклику призведе до недійсного SQL. Використовуйте AsEnumerable або AsAsyncEnumerable одразу після FromSql або FromSqlRaw, щоб переконатися, що EF Core не намагається компонувати код поверх збереженої процедури.

## Відстеження змін

Запити, що використовують FromSql або FromSqlRaw, дотримуються тих самих правил відстеження змін, що й будь-які інші запити LINQ в EF Core. Наприклад, якщо запит проектує типи сутностей, результати відстежуються за замовчуванням. У наступному прикладі використовується SQL-запит, який вибирає значення з табличної функції (TVF), а потім вимикає відстеження змін за допомогою виклику AsNoTracking:

```cs
var searchTerm = "Lorem ipsum";

var blogs = await context.Blogs
    .FromSql($"SELECT * FROM dbo.SearchBlogs({searchTerm})")
    .AsNoTracking()
    .ToListAsync();
```

## Запити скалярних (несутнісних) типів

Хоча FromSql корисний для запитів сутностей, визначених у вашій моделі, SqlQuery дозволяє легко запитувати скалярні, несутнісні типи через SQL, без необхідності переходити до API доступу до даних нижчого рівня. Наприклад, наступний запит отримує всі ідентифікатори з таблиці Blogs:

```cs
    var query = context.Database
    .SqlQuery<int>($"SELECT [BlogId] FROM [Blogs]");

    Console.WriteLine(query.ToQueryString());

    var ids = await query.ToListAsync();

    foreach (var id in ids)
    {
        Console.WriteLine($"BlogId:{id}");
    }
```
```
SELECT [BlogId] FROM [Blogs]

BlogId:1
BlogId:2
BlogId:3
```
Ви також можете створювати оператори LINQ над вашим SQL-запитом. Однак, оскільки ваш SQL стає підзапитом, на вихідний стовпець якого мають посилатися додавання SQL EF, ви повинні назвати вихідний стовпець Value. Наприклад, наступний запит повертає ідентифікатори, які перевищують середнє значення ідентифікаторів:

```cs
    var query = context.Database
    .SqlQuery<int>($"SELECT [BlogId] AS [Value] FROM [Blogs]")
    .Where(id => id > context.Blogs.Average(b => b.BlogId));

    var ids = await query.ToListAsync();

    Console.WriteLine(query.ToQueryString());

    foreach (var id in ids)
    {
        Console.WriteLine($"BlogId:{id}");
    }
```
```sql
SELECT [s].[Value]
FROM (
    SELECT [BlogId] AS [Value] FROM [Blogs]
) AS [s]
WHERE CAST(CAST([s].[Value] AS int) AS float) > (
    SELECT AVG(CAST([b].[BlogId] AS float))
    FROM [Blogs] AS [b])
BlogId:3
```
SqlQuery можна використовувати з будь-яким скалярним типом, що підтримується вашим постачальником бази даних. Якщо ви хочете використовувати тип, який не підтримується вашим постачальником бази даних, ви можете скористатися конфігурацією перед узгодженням, щоб визначити для нього перетворення значень.

SqlQueryRaw дозволяє динамічну побудову SQL-запитів, так само як FromSqlRaw робить для типів сутностей.

## Виконання SQL без запитів

У деяких сценаріях може знадобитися виконати SQL, який не повертає жодних даних, зазвичай для зміни даних у базі даних або виклику збереженої процедури, яка не повертає жодних наборів результатів.

```cs
var rowsModified = context.Database.ExecuteSql($"UPDATE [Blogs] SET [Url] = NULL");
```
Це виконує наданий SQL-запит і повертає кількість змінених рядків. ExecuteSql захищає від SQL-ін'єкцій, використовуючи безпечну параметризацію, як і FromSql, а ExecuteSqlRaw дозволяє динамічно створювати SQL-запити, як і FromSqlRaw для запитів.

## Обмеження

Існує кілька обмежень, про які слід пам'ятати під час повернення типів сутностей із SQL-запитів:

* SQL-запит повинен повертати дані для всіх властивостей типу сутності.
* Назви стовпців у результуючому наборі повинні збігатися з іменами стовпців, на які зіставлено властивості.
* SQL-запит не може містити пов’язані дані. Однак у багатьох випадках його можна створювати поверх запиту за допомогою оператора Include, щоб повернути пов’язані дані (див. розділ «Включення пов’язаних даних»).
