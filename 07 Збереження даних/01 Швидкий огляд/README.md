# Збереження даних

Хоча запити дозволяють зчитувати дані з бази даних, збереження даних означає додавання нових сутностей до бази даних, видалення сутностей або зміну властивостей існуючих сутностей певним чином. Entity Framework Core (EF Core) підтримує два фундаментальні підходи до збереження даних у базі даних.


## Підхід 1: відстеження змін та збереження змін

У багатьох сценаріях вашій програмі потрібно запитувати деякі дані з бази даних, виконувати деякі зміни та зберігати ці зміни; це іноді називають «одиницею роботи». Наприклад, припустимо, що у вас є набір блогів, і ви хочете змінити властивість Url одного з них. В EF це зазвичай робиться так:

```cs
    var blog = await context.Blogs.SingleAsync(b => b.Url == "https://example.com");
    blog.Url = "http://example.com/blog";
    await context.SaveChangesAsync();
    Console.WriteLine("Updated blog with ID " + blog.BlogId);
```
```
Updated blog with ID 1
```

Наведений вище код виконує такі кроки:

1. Він використовує звичайний запит LINQ для завантаження сутності з бази даних. Запити EF відстежуються за замовчуванням, тобто EF відстежує завантажені сутності у своєму внутрішньому трекері змін.
2. Завантажений екземпляр сутності змінюється як завжди, шляхом призначення властивості .NET. EF не бере участі в цьому кроці.
3. В кінці, викликається DbContext.SaveChanges(). На цьому етапі EF автоматично виявляє будь-які зміни, порівнюючи об'єкти зі знімком з моменту їх завантаження. Будь-які виявлені зміни зберігаються в базі даних; під час використання реляційної бази даних це зазвичай передбачає надсилання, наприклад, SQL UPDATE для оновлення відповідних рядків.

Зверніть увагу, що вищеописане описувало типову операцію оновлення існуючих даних, але аналогічні принципи застосовуються для додавання та видалення сутностей. Ви взаємодієте з трекером змін EF, викликаючи DbSet\<TEntity\>.Add та Remove, що призводить до відстеження змін. Потім EF застосовує всі відстежені зміни до бази даних, коли викликається SaveChanges() (наприклад, через SQL INSERT та DELETE під час використання реляційної бази даних).

SaveChanges() пропонує такі переваги:

* Вам не потрібно писати код для відстеження змінених сутностей та властивостей — EF робить це автоматично за вас та оновлює лише ці властивості в базі даних, покращуючи продуктивність. Уявіть, що ваші завантажені сутності прив'язані до компонента інтерфейсу користувача, що дозволяє користувачам змінювати будь-яку властивість, яку вони бажають; EF знімає тягар з'ясування того, які сутності та властивості були фактично змінені.
* Збереження змін у базі даних іноді може бути складним! Наприклад, якщо ви хочете додати блог і деякі публікації для цього блогу, вам може знадобитися отримати ключ, згенерований базою даних, для вставленого блогу, перш ніж ви зможете вставити публікації (оскільки вони повинні посилатися на блог). EF робить все це за вас, позбавляючи вас складності.
* EF може виявляти проблеми паралельного виконання, наприклад, коли рядок бази даних був змінений кимось іншим між вашим запитом та SaveChanges(). Докладнішу інформацію можна знайти в розділі Конфлікти паралельного виконання.
* У базах даних, які підтримують цю функцію, SaveChanges() автоматично обгортає кілька змін у транзакції, забезпечуючи узгодженість даних у разі виникнення помилки. Докладніше див. у розділі Транзакції.
* SaveChanges() також у багатьох випадках об’єднує кілька змін, що значно зменшує кількість циклів обробки даних та значно покращує продуктивність. Докладнішу інформацію можна знайти в розділі «Ефективне оновлення».

Щоб отримати додаткові відомості та зразки коду щодо базового використання SaveChanges(), див. розділ Базові SaveChanges. Щоб отримати додаткові відомості про відстеження змін EF, див. огляд відстеження змін.

## Підхід 2: ExecuteUpdate та ExecuteDelete ("масове оновлення")

Хоча відстеження змін та SaveChanges() є потужним способом збереження змін, вони мають певні недоліки.

По-перше, SaveChanges() вимагає, щоб ви надсилали запит і відстежували всі сутності, які ви збираєтеся змінити або видалити. Якщо вам потрібно, скажімо, видалити всі блоги з рейтингом нижче певного порогу, ви повинні запитувати, матеріалізувати та відстежувати потенційно величезну кількість рядків, а також використовувати SaveChanges() для генерації інструкції DELETE для кожного з них. Реляційні бази даних пропонують набагато ефективнішу альтернативу: можна надіслати одну команду DELETE, яка вказує, які рядки видалити, за допомогою речення WHERE, але модель SaveChanges() не дозволяє це зробити.

Для підтримки цього сценарію "масового оновлення" можна використовувати ExecuteDelete наступним чином:

```cs
context.Blogs.Where(b => b.Rating < 3).ExecuteDelete();
```
Це дозволяє вам виразити SQL-інструкцію DELETE за допомогою звичайних операторів LINQ – подібно до звичайного запиту LINQ – що призводить до виконання наступного SQL-запиту для бази даних:

```sql
DELETE FROM [b]
FROM [Blogs] AS [b]
WHERE [b].[Rating] < 3
```
Це дуже ефективно виконується в базі даних, без завантаження будь-яких даних з бази даних або залучення відстеження змін EF. Аналогічно, ExecuteUpdate дозволяє вам виразити SQL-інструкцію UPDATE.

Навіть якщо ви не змінюєте сутності масово, ви можете точно знати, які властивості якої сутності потрібно змінити. Використання API відстеження змін для виконання змін може бути надто складним, вимагаючи створення екземпляра сутності, відстеження його через Attach, внесення змін і, нарешті, виклику SaveChanges(). Для таких сценаріїв ExecuteUpdate та ExecuteDelete можуть бути значно простішим способом вираження тієї ж операції.

Зрештою, як відстеження змін, так і сама функція SaveChanges() накладають певні накладні витрати на виконання. Якщо ви пишете високопродуктивний застосунок, ExecuteUpdate та ExecuteDelete дозволяють уникнути обох цих компонентів та ефективно генерувати потрібний вам оператор.

Однак, зверніть увагу, що ExecuteUpdate та ExecuteDelete також мають певні обмеження:

* Ці методи виконуються негайно, і наразі їх не можна об'єднувати з іншими операціями. З іншого боку, SaveChanges() може об'єднувати кілька операцій разом.

* Оскільки відстеження змін не передбачається, ви несете відповідальність за те, щоб точно знати, які сутності та властивості потрібно змінити. Це може означати більше ручного, низькорівневого відстеження коду, що потрібно змінювати, а що ні.

* Крім того, оскільки відстеження змін не задіяне, ці методи не застосовують автоматично керування паралельністю під час збереження змін. Однак, ви все ще можете явно додати речення Where, щоб самостійно реалізувати керування паралельністю.

* Наразі підтримується лише оновлення та видалення; вставку необхідно виконувати через DbSet\<TEntity\>.Add та SaveChanges().

## Підсумок

Нижче наведено кілька рекомендацій щодо того, коли використовувати який підхід. Зауважте, що це не абсолютні правила, але корисні емпіричні принципи:

* Якщо ви заздалегідь не знаєте, які зміни відбудуться, скористайтеся функцією SaveChanges; вона автоматично визначить, які зміни потрібно застосувати. Приклади сценаріїв:
    * "Я хочу завантажити блог з бази даних та відобразити форму, яка дозволить користувачеві змінити його"

* Якщо вам потрібно маніпулювати графом об'єктів (тобто кількома взаємопов'язаними об'єктами), використовуйте SaveChanges; він визначить правильний порядок змін і те, як все пов'язати між собою.
    * «Я хочу оновити блог, змінивши деякі його публікації та видаливши інші»

* Якщо ви хочете змінити потенційно велику кількість сутностей на основі певного критерію, використовуйте ExecuteUpdate та ExecuteDelete. Приклади сценаріїв:
    * «Я хочу підвищити зарплату всім співробітникам»
    * «Я хочу видалити всі блоги, назва яких починається на літеру X»

* Якщо ви вже точно знаєте, які об'єкти хочете змінити та як саме, використовуйте ExecuteUpdate та ExecuteDelete. Приклади сценаріїв:
    * «Я хочу видалити блог під назвою «Фу»»
    * «Я хочу змінити назву блогу з ідентифікатором 5 на «Bar»»
